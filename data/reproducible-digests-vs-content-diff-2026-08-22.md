# Reproducible Digests vs. Content-Diff Publishing in Hardened Image Catalogues

Research input, received 2026-08-22, cited by design.md Key Design Decision 6 (cluster A, revision finding A1).

## TL;DR
- The industry has **not** converged on bit-for-bit reproducible digests as the mechanism for "nothing changed." The dominant real-world pattern is **rebuild-always + digest-pin + bot-mediated update PRs** (Chainguard's digestabot model), with reproducibility used mainly as an *audit/verification* property, not as a publish gate. Only apko/Nix/Bazel-class tools reliably achieve digest-stable rebuilds; general Dockerfile/BuildKit pipelines — including third-party frontends like `dhi.io/build` — do not, and no major vendor publicly guarantees no-op-rebuild digest stability.
- For your specific situation (BuildKit + opaque third-party frontend, non-reproducible today), the **Syft-based content-diff publish gate is the pragmatic and lower-risk choice**. It matches what Chainguard's own `chainctl images diff` and CI SBOM-diff tooling already do, and it sidesteps the long tail of BuildKit nondeterminism you cannot control inside a black-box frontend. Reproducibility should be a *later, additive* goal, verified with `diffoci`/`crane`, not a prerequisite for suppressing churn.
- The main risk in the content-diff approach is **SBOM nondeterminism itself** (Syft ordering/CPE/Go-module instability historically) — mitigate by comparing a **canonicalised, sorted (name, version) set** rather than raw SBOM bytes, and by treating base-layer digest changes as a separate signal. Package-set equality can miss meaningful changes (rebuilt binaries with identical versions, compiler/flag changes), so pair it with a base-image digest check.

## Key Findings

1. **apko (Chainguard/Wolfi) is the reference implementation of digest-stable rebuilds.** apko is "fully reproducible by default — run apko twice and you will get exactly the same binary," achieved through zeroed file timestamps, sorted/deterministic tar construction, fixed uid/gid, sorted env vars, and a locked package set. Yet Chainguard **still rebuilds daily and still mints new digests**, because their configs *float forward* (unlocked) to pick up CVE fixes. They solve downstream churn socially/operationally with **digestabot** (bot opens a PR to bump the pin; a human approves), not by suppressing rebuilds.

2. **Reproducibility and "nothing changed" are decoupled in practice.** Chainguard's reproducibility is a *verification* tool ("anyone can re-run the build and get the same digest" from the locked apko config attestation), not the mechanism they use to avoid republishing. When they need to know whether a new digest is meaningful, they use **crane** to diff manifests/configs/filesystems, and expose **`chainctl images diff`** which "compares SBOM packages and vulnerability scans." This is exactly your Option A.

3. **Docker Hardened Images do not claim digest-stable rebuilds.** The `dhi.io/build:2` system is a self-hosting BuildKit frontend driven by a "continuous, event-driven build system." DHI docs and the catalog wiki define "reproducibility" narrowly as *input pinning* (commit SHAs, digest-pinned bases, consistent embedded build dates via Go `-X` flags and `SETUPTOOLS_SCM_PRETEND_VERSION`) — **not** bit-identical output digests. There is **no DHI mention of SOURCE_DATE_EPOCH, rewrite-timestamp, or provenance mode=reproducible**, and **no documented "nothing changed" signal**; consumers track updates via mutable version tags, digest pinning, mirroring into a `dhi-` prefixed repo, and Docker Hub **webhooks**. This validates that even a well-resourced BuildKit-frontend catalogue does *not* rely on digest equality.

4. **BuildKit's reproducibility knobs work but have a documented long tail of failure modes.** `SOURCE_DATE_EPOCH` (v0.11, metadata only) plus `rewrite-timestamp=true` (v0.13, rewrites file mtimes in the image exporter) get you close, but known gaps remain: `rewrite-timestamp` only affects the image exporter (not intermediate `COPY --from` into `scratch`, per moby/buildkit#6348), and apt/apk logs (`/var/log/apt/history.log`, `alternatives.log`), `ldconfig` aux-cache, overlayfs whiteouts, and non-snapshotted package repos all reintroduce nondeterminism. Independent reproducers (Dangerzone/Freedom of the Press) confirm you frequently still get diffs and must hunt them down.

5. **Kaniko's `--reproducible` is a cautionary tale for opaque tooling.** Multiple open issues show `--reproducible` still yields different digests (atime/ctime in tar, layer differences, even panics), and it strips useful `docker history`. This is the concrete failure mode you fear from a black-box frontend: a "reproducible" flag that doesn't actually reproduce.

6. **SBOM-diff as a publish/notify gate is an established, tooled practice.** `chainctl images diff`, `cyclonedx-cli diff --component-versions`, `sbomdiff`, CycloneDX `sbom-comparator`, and GitHub Actions that "fetch and diff CycloneDX SBOMs for container images, posting comments or opening PRs when package or vulnerability changes are detected" all exist. The caveat is SBOM generator nondeterminism: Syft has a history of ordering/CPE instability (anchore/syft #331, #2967), so you must normalise before comparing.

## Details

### 1. Chainguard / Wolfi / apko — the reproducible-digest camp (used for verification, not publish-gating)

**Mechanism.** apko builds OCI images directly from apk packages with no Dockerfile. Its README states it is "fully reproducible by default. Run apko twice and you will get exactly the same binary." The Chainguard tutorial confirms: "apko generated images are reproducible — run the same build with the same inputs and you will get bitwise identical output. This is something that is currently impossible to do with Docker." The `rawkode.academy` walkthrough describes the concrete mechanisms: "apko emits per-architecture OCI tarballs plus an OCI image index, all reproducible… apko zeroes file timestamps and source-of-build metadata by default precisely to make this work." apko's NEWS.md documents deliberate determinism fixes: "Environment variables in the image configuration are now sorted for reproducibility," a `--lockfile` flag for "strict versions," per-package checksums in the lockfile, and fixes for "duplicate file entries in installed DB and SBOMs."

**The lockfile boundary.** In `chainguard-images/images`, each image ships a `locked_config.json` — "a fully resolved apko configuration — exact package versions, accounts, entrypoint, environment, and annotations — for each supported architecture. Because the package versions are pinned, builds are reproducible: the same locked_config.json produces the same image content." Reproduction is proven by downloading the signed `https://apko.dev/image-configuration` attestation and re-running `apko publish`, yielding an identical digest.

**Documented caveats (from Chainguard's own CTO, Matt Moore).** Even apko reproducibility has limits: (a) "Different versions of the underlying tooling may change subtle things (e.g. compression levels)"; (b) if a package is withdrawn, reproduction fails; (c) Wolfi is a rolling repo that does not keep old package versions long, so historical reproduction requires archived apks; (d) the apks themselves embed Wolfi's signing signatures, so you cannot rebuild byte-identical apks from source. The Academy video makes this explicit: "in six months time, I'm unlikely to be able to download some of these packages at these exact versions."

**How they handle churn — this is the crux for you.** Chainguard **does not** avoid new digests. "Chainguard Containers are rebuilt daily… we recommend a development pattern where digests are used… and are regularly updated by a bot… We do this ourselves with our digestabot tool," requiring human approval of each bump. Critically: digestabot only opens a PR when *the tag's digest changed but the tag stayed the same*; "if both the tag and digest change, digestabot will not open a PR." So the daily rebuild → new-digest → bot-PR → human-approve loop is the accepted operating model, and reproducibility is not used to suppress it. Their advice: for "true immutability, use image digests"; epoch tags "can change over time."

**When they need "did anything actually change?"** they diff. `chainctl images diff … --output markdown` "compares SBOM packages and vulnerability scans and requires Grype on PATH," and the OneUptime writeup adds a precise epistemics caveat that applies to *your* Option A too: "A changed digest proves that the referenced manifest or index bytes changed, but not necessarily that package or application contents changed. Unchanged application source does not prove a base rebuild is behaviorally identical." For hunting down unwanted digest changes they use crane's diff recipes on manifests, configs, and filesystems.

**melange** builds the apks reproducibly upstream of apko; keyless CI signs each apk with an ephemeral per-run key. This gives Chainguard a package-level determinism foundation that Debian/RPM ecosystems lack.

### 2. Docker Hardened Images (DHI) — event-driven BuildKit frontend, no digest-stability claim

DHI is the closest analogue to your project. The catalog is built by `dhi.io/build:2`, "a custom build system… which serves as both the build infrastructure and a Docker BuildKit frontend. This system is self-hosting." Images are invoked via `# syntax=dhi.io/build:2-alpine3.22` and built with `docker buildx build … --sbom=generator=dhi.io/scout-sbom-indexer:1 --provenance=1`. The frontend itself is compiled from `github.com/docker-hardened-images/frontend` Go source and is the entrypoint that builds every other catalog image (a bootstrap/self-hosting scenario).

**Attestations.** Every DHI (including the free Community tier) ships "a complete SBOM, SLSA Build Level 3 provenance attestations, a cryptographic signature, and OpenVEX exploitability data," in both CycloneDX and SPDX, bound to the image digest. Verified via `docker scout attest get --predicate-type … --verify`.

**Reproducibility posture.** Per the catalog wiki, "build reproducibility ensures that rebuilding an image from the same source produces identical outputs," but the *mechanisms* listed are all input-pinning: commit-SHA pinning, SHA256 digest references for bases/artifacts, keyring verification, "the embedded build date is consistent across rebuilds," Go `-X` linker flags, and `SETUPTOOLS_SCM_PRETEND_VERSION`. There is **no** DHI-specific mention of SOURCE_DATE_EPOCH, rewrite-timestamp, or `provenance mode=reproducible`, and **no published test asserting two rebuilds of unchanged content yield the same digest.** DHI's docs describe consumer-facing *immutability* (a given digest never changes) — which is standard OCI semantics, not rebuild-stability.

**Rebuild cadence.** "Docker Hardened Images use a continuous, event-driven build system that automatically rebuilds images whenever upstream fixes become available." Docker Scout "continuously ingests CVE information… The moment CVE data becomes available, Scout begins analysis," and "cascading builds" rebuild all dependent images. Select/Enterprise tiers carry a 7-day critical-CVE patch SLA. For *customized* images, "when the base Docker Hardened Image receives a security patch… Docker automatically rebuilds your customized images in the background."

**How consumers track updates.** Consumers **mirror** a DHI repo into their org (it appears "prefixed by `dhi-`, and continues to receive updated images"), can configure **Docker Hub webhooks**, and pin digests. A CLI equivalent (`docker dhi mirror list`) shows source/destination repos and mirroring status. There is **no documented "nothing changed between rebuilds" signal** — digest comparison is the only recourse, and because tags are republished to new digests, a moved tag does not by itself tell you whether contents changed. **Gap:** Docker does not publicly state whether an unchanged-content rebuild reuses the prior digest or mints a new one; the event-driven triggering implies rebuilds normally accompany real changes.

**Implication for you:** the most directly comparable commercial project — same BuildKit-frontend architecture — does **not** lean on reproducible digests to answer "did anything change." That is strong evidence the reproducible-digest route is not a prerequisite.

### 3. Other commercial hardened-image vendors

- **Red Hat UBI / Konflux / "Hummingbird" (RHEL hardened images).** Per Red Hat's Customer Portal, "Red Hat aims to re-build and distribute available Red Hat UBI images on a 6 weekly cadence, or sooner if triggered by the release of a CVE rated as Critical or Important." Red Hat has invested heavily in *actual* reproducibility for its newer Konflux-based pipeline: Project Hummingbird images are "built once in Konflux, and then rebuilt once more outside of it" and byte-compared, using Buildah 1.41's `--source-date-epoch` and `--rewrite-timestamp`. Red Hat states Hummingbird "pioneered a build process based on Konflux that makes it easier for third parties and customers to verify provenance and reproduce builds," while "UBI uses a different, legacy RHEL build process" (not reproducible). RHEL 10 docs give an explicit `buildah bud --source-date-epoch --rewrite-timestamp` recipe and note "buildah inspect should show the same image digest." Konflux uses Tekton Chains for signed SLSA provenance and a "neutral observer/attester" rebuild-and-compare pattern. This is the one vendor pursuing reproducible digests seriously — and notably they *verify* via rebuild-and-diff, not publish-gate.
- **SUSE BCI.** Built via the Open Build Service (OBS), a distribution build platform; OBS emphasises deterministic, source-driven package builds, but I did not find a public BCI claim of bit-identical container-image digests. (Evidence thin — flagged.)
- **Canonical Chiselled Ubuntu / Ubuntu Pro.** "Chisel" installs versioned *slices* of Ubuntu debs into a `FROM scratch` image; "Chisel slices are versioned… allowing you to rebuild the same image consistently." Canonical's container build service drives "regular updates" via pipeline automation. Reproducibility is framed as slice-version consistency, not a byte-identical-digest guarantee. Backed by 5-year (12–15-year Pro) maintenance.
- **Google Distroless / Bazel.** Distroless is built with Bazel (`rules_docker`, now `rules_oci` + `rules_distroless`). Bazel images "are deterministic / reproducible." `rules_distroless` uses a `lock.json` pinning "exact package versions, URLs, and SHA256 hashes… once generated, builds are deterministic," and constructs tar layers with `DEFAULT_TIME="0.0"`, `DEFAULT_UID/GID=0`, and declaration-order file addition via BSD tar/mtree. Bazel's content-addressed, hermetic model means unchanged inputs → cache hit → identical output, so "nothing changed" is answered by the build graph itself.
- **RapidFort, Minimus, Echo.** These "rebuild-from-source" vendors (Minimus: "rebuilds packages when maintainers publish new releases, and pushes fresh images after automated testing and signing"; Echo: "continuously rebuilds container base images from scratch") emphasise CVE-free freshness and signing/SBOM/VEX, with rolling-release cadence. None publicly documents bit-for-bit reproducible digests or a no-op-rebuild suppression mechanism; their model is roll-forward-and-retest. (Reproducibility claims here are thin/unverifiable — flagged.)
- **Bitnami Secure Images (VMware/Broadcom).** Hardened Photon-based builds with VEX/KEV, SBOMs; "closely tracks upstream source changes and promptly publishes new versions… using automated systems." No public reproducible-digest claim. (After Aug/Sep 2025 the free Debian catalog moved to `bitnamilegacy`; secure images are `latest`-only in the free tier.)

### 4. Open-source / upstream practice

- **Debian Reproducible Builds.** State of the art after ~a decade: per Reproducible Builds project data (cited in arXiv:2505.21642), "As of November 2023, Debian leads… with 95.2% of their Bookworm/amd64 packages being reproducible[;] 75.8% of all Arch Linux packages are reproducible." `reproduce.debian.net` and `debian-repro-status` track it, and the release team plans penalties in "forky" (Debian 14) for regressions and a future move from "should" to "must." Per LWN's Aug-2024 status writeup, "Nearly 4000 bugs have been fixed… there are still around 300 patches pending… the project has discovered 430 different problems that lead to non-reproducible builds, which are documented in the reproducible-notes repository" — timestamps, build paths, file ordering, locale, parallelism, and embedded build-ids being the hard ones. **diffoscope** is the canonical recursive-diff tool. Lesson for you: even a decade-long, well-funded effort treats bit-for-bit as a *gradually-approached* property, not a switch.
- **Nix.** dockerTools `buildLayeredImage`/`streamLayeredImage` use a static creation date by default "to produce reproducible images"; setting `created = "now"` deliberately breaks byte-reproducibility for a human-readable date. Nix's content-addressed derivations answer "nothing changed" at the store-path level (input hash → output). The definitive study — Malka, Zacchiroli & Zimmermann, *"Does Functional Package Management Enable Reproducible Builds at Scale? Yes."* (MSR 2025 / arXiv:2501.15919) — rebuilt 709,816 nixpkgs packages and obtained "very high bitwise reproducibility rates, between 69 and 91% with an upward trend [69% in 2017 → 91% in April 2023], and even higher rebuildability rates, over 99%." Of the irreproducible packages, a total of 19.7% were caused by four categories: embedded timestamps (14.8%), embedded environment variables (2.2%), embedded build IDs (2.2%), and uname outputs (1.3%). The same authors report 99.99% reproducibility of *build environments*. `nix2container` skips already-pushed layers — an elegant "don't republish unchanged layers" model.
- **BuildKit.** SOURCE_DATE_EPOCH since v0.11 (Jan 2023, metadata only); file-timestamp rewriting via `rewrite-timestamp=true` since v0.13. Buildx auto-propagates the env var. Documented limits: rewrite-timestamp affects only the image exporter (moby/buildkit#6348); the official-images reproducibility issue (#16044) enumerates required manual cleanups (`/var/log/apt/history.log`, `alternatives.log`, `/var/cache/ldconfig/aux-cache`) and notes "reproducing apk packages is still challenging, as Alpine does not have snapshot servers."
- **Buildah/Podman:** `--source-date-epoch` + `--rewrite-timestamp` (Buildah 1.41) — the same model, now used in production by Red Hat.
- **Kaniko:** `--reproducible` is documented as unreliable — issues #710, #900, #2005, #2304 (differing digests despite the flag, atime/ctime in tar, layer differences), #2537 (panic), and it strips `docker history`. Also non-deterministic layer count with default snapshot mode.
- **ko (Go)** and **Jib (Java)** are reproducible by design (fixed timestamps, no daemon), the gold standard for single-language images.
- **Package-DB determinism.** apk installed-DB determinism is what makes apko reproducible; Debian/RPM do not guarantee byte-identical installed databases across runs (install order, timestamps, log files), which is precisely why Wolfi/apko exists and why Debian's reproducibility effort is so laborious. For your apk-based images this is favourable; for any Debian/glibc variants it is a real risk area.

### 5. The downstream churn problem

This is the actual pain point, and the ecosystem's answer is **tooling + policy, not reproducibility.**

- **Renovate** supports `pinDigests: true`, which "opens a PR whenever the upstream image is rebuilt under the same tag" — the desired behaviour, but "digest pinning increases PR volume noticeably, because popular base images are rebuilt frequently." Recommended mitigations: group digest updates with `packageRules` matching `updateTypes: ["digest"]` into a single weekly PR for non-critical images; keep critical bases on a daily group; schedule windows; `prConcurrentLimit`/`prHourlyLimit`. Renovate cannot natively tell a no-op rebuild from a substantive one — it only sees the digest changed.
- **Dependabot** does not support Chainguard's `cgr.dev` registry; Renovate is preferred there.
- **digestabot** (Chainguard) and **frizbee** (Stacklok) are purpose-built digest bumpers. Bret Fisher's "silent-rebuilds" repo is the canonical writeup comparing Dependabot/Renovate/digestabot for exactly this "many official images are periodically rebuilt without changing the tag version" problem, and confirms the industry norm: rebuild frequently, pin digests, automate the bump, gate on one human-approved PR.
- The **content-diff-before-notify** idea is exactly what the GitHub Action that "fetches and diffs CycloneDX SBOMs for container images, posting comments or opening pull requests when package or vulnerability changes are detected" implements, and what `chainctl images diff` gives Chainguard internally.

### 6. SBOM-diff as a publish gate — tooling and pitfalls

**Tooling that exists:** `chainctl images diff` (SBOM packages + vuln scans); `cyclonedx-cli diff sbom-a sbom-b --component-versions`; `sbomdiff` (SPDX + CycloneDX: version/license/added/removed); CycloneDX `sbom-comparator`; `sbom-tools diff` (semantic, fuzzy PURL matching). So Option A is well-trodden.

**Pitfall 1 — SBOM generator nondeterminism.** Syft has documented history of unstable output: anchore/syft #331 ("Running BOM generation twice on the same image results in different output each time"), fixed by sorting; #2967 ("nondeterministic behavior… order CPEs deterministically for SBOM reproducibility"). SPDX/CycloneDX documents also carry UUIDs and timestamps by default. **Therefore do not diff SBOM bytes** — extract and diff a canonicalised, sorted `(name, version)` (and ideally `(type, name, version)`) set, exactly as your proposed comparator does. Syft's own guidance is `syft -o json | jq '.artifacts | sort_by(...)'`.

**Pitfall 2 — package-set equality misses real changes.** As the Chainguard/OneUptime caveat states, identical package versions do **not** prove identical bytes: a dependency rebuilt at the same version, a compiler/flag change, or a base-layer change can alter behaviour without moving any `(name, version)` pair. Go modules from binary build-info are generally stable (versions are embedded), but `-trimpath`/build-id differences won't show in a name+version diff. **Mitigation:** combine your SBOM package-set comparator with a **base-image digest check** and, where feasible, a Go build-info/VCS-stamp check, so a same-version-but-rebuilt-base still triggers a publish.

### 7. Verdict material — can a BuildKit + third-party-frontend pipeline get bit-identical rebuilds?

Evidence says: **possible in principle, unreliable in practice when the frontend is a black box you don't control.**

- BuildKit *can* reproduce (SOURCE_DATE_EPOCH + rewrite-timestamp + provenance mode=reproducible), and Red Hat's Konflux/Buildah pipeline proves a production-grade RPM/Debian pipeline can be made reproducible — but they achieved it by *owning* the build steps and continuously rebuild-and-diffing with diffoci to hunt regressions ("achieving reproducibility is not a one-time task… requires constant upkeep").
- Your specific unknowns — whether the frontend's apk steps produce byte-identical package DBs, whether generated files (CA bundles) are stably ordered, whether Go builds use `-trimpath`/fixed build-ids — are precisely the classes that break reproducibility (Debian's 430 catalogued causes; kaniko's repeated failures; the official-images cleanup list of logs/caches). You cannot fix these from outside a closed frontend.
- Independent reproducers (Dangerzone, Freedom of the Press `repro-build`) confirm you routinely still get diffs even with the documented flags and must diagnose them one by one with diffoci/diffoscope.

**Conclusion:** demanding bit-identical digests as your "nothing changed" oracle makes you hostage to a black box. The SBOM package-set comparator gives you a robust, vendor-validated "did the thing consumers care about change?" signal today, independent of frontend nondeterminism. Pursue reproducibility in parallel as a *verification* asset (and to shrink registry storage / speed diffs), verified with diffoci — but don't block your churn fix on it.

## Comparison Table

| Approach | Who uses it | "Nothing changed" test | Handles frontend nondeterminism? | Downstream churn control |
|---|---|---|---|---|
| **Bit-for-bit reproducible digest** | apko/Chainguard (verification), Nix, Bazel/Distroless, ko/Jib, Red Hat Konflux/Hummingbird | Digest equality | Only if you own/trust every build step | High *if* achieved; else useless |
| **Content-diff / SBOM package-set gate** | Chainguard `chainctl images diff`, CI SBOM-diff Actions, Bitnami-style | Sorted (name,version) set equality (+ base digest) | Yes — independent of build nondeterminism | Publish only on real change → fewer pins |
| **Schedule/event rebuild + digest-pin + bot PR** | Chainguard digestabot, DHI (mirror+webhook), most vendors | None — every rebuild is a new digest; humans/bots absorb it | N/A (doesn't try) | Grouping/scheduling in Renovate; human-approved PR |
| **Content-addressed build graph** | Nix, Bazel | Input-hash / cache hit | Yes (hermetic) | Unchanged inputs never rebuild/republish |

## Recommendations

**Stage 1 — ship the content-diff publish gate now (Option A).** Implement the Syft comparator against a **canonicalised, sorted `(type, name, version)` set** per platform manifest (apk + Go build-info modules), compared to the SBOM attested to the currently published digest for the same release tag. On equality: publish nothing. On difference: publish, scan, sign, attest, tag, open the chart-pin PR. This is precisely what `chainctl images diff` and the CycloneDX-diff GitHub Actions already do, and it is immune to the BuildKit/frontend nondeterminism you cannot control.
- **Guardrails:** never diff raw SBOM bytes (Syft ordering/UUID/timestamp instability, anchore/syft #331/#2967). Normalise first. Persist the normalised set as its own attestation so future comparisons don't re-run Syft on the old image.
- **Add a base-image digest check** alongside the package-set diff so a same-version base rebuild still triggers a publish (covers the "package set unchanged but bytes changed" blind spot).

**Stage 2 — reduce PR blast radius downstream.** Regardless of publish logic, adopt Chainguard's operating model for consumers: digest pins + a bot (digestabot/Renovate with `pinDigests`) + **grouped, scheduled** digest PRs (`updateTypes: ["digest"]`, weekly for non-critical, daily for critical). Your Stage-1 gate means these PRs now correspond to *real* changes, which is the whole point.

**Stage 3 — pursue reproducibility as a verification asset, not a gate.** Turn on `SOURCE_DATE_EPOCH=<commit time>`, `rewrite-timestamp=true`, and `--provenance mode=max,reproducible=true`, then **measure** with `diffoci` (or crane's diff recipes) across two clean rebuilds. Track the residual diff classes (expect: apk/apt logs, ldconfig aux-cache, CA-bundle ordering, Go build-ids). Fix what you can; document what you can't.

**Benchmarks that would change the recommendation:**
- If `diffoci` shows **zero residual diff across ≥95% of images over a 2-week window**, promote digest-equality to the *primary* gate and demote SBOM-diff to a cross-check (cheaper, stronger).
- If the frontend adds documented SOURCE_DATE_EPOCH/rewrite-timestamp support and Go `-trimpath`, re-test immediately.
- If SBOM-diff ever passes while `diffoci` shows a functional change (rebuilt binary, changed base), tighten the gate to include base-digest + build-id, or fall back to digest-equality for affected image families.

## Caveats
- **Vendor reproducibility claims are unevenly verifiable.** apko/Chainguard, Nix, Bazel/Distroless, and Red Hat Konflux/Hummingbird publish concrete, reproducible mechanisms and (for Chainguard/Red Hat) show their work. Minimus, Echo, RapidFort, Bitnami, and SUSE BCI make freshness/hardening claims but I found **no public bit-for-bit reproducible-digest evidence** for them — treat as unverified.
- **DHI gaps are real, not oversight.** Docker does not publicly document whether an unchanged-content rebuild reuses the prior digest, nor any SOURCE_DATE_EPOCH/rewrite-timestamp usage in `dhi.io/build`. My conclusion that DHI likely mints new digests per rebuild is an inference from the event-driven model plus the absence of any digest-stability claim, not a documented fact.
- **SBOM package-set equality is a proxy, not proof.** It can both over-fire (SBOM tool noise — mitigated by normalisation) and under-fire (identical versions, different bytes — mitigated by base-digest/build-id checks). The OneUptime/Chainguard caveat that "a changed digest… [does] not necessarily [mean] package or application contents changed" cuts both ways.
- **Reproducibility percentages cited** (Nix 69–91% bitwise / >99% rebuildable per Malka et al. 2025; Debian 95.2% Bookworm/amd64 as of Nov 2023) are from specific studies/snapshots and will drift; treat as directional.
- I did not obtain a primary DHI statement on digest stability or a SUSE BCI reproducibility statement; both are flagged as thin.
