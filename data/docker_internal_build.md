# The Real Toolchain Behind Docker Hardened Images (DHI): A Practical Breakdown for DHI Engineering Work

## TL;DR
- **DHI is NOT built with Chainguard's apko/melange.** Primary-source evidence from Docker's open catalog (`github.com/docker-hardened-images/catalog`) shows DHI is produced by a **proprietary, self-hosting Docker BuildKit frontend called `dhi.io/build`** (compiled from the Go source at `docker-hardened-images/frontend`), driven by declarative YAML definitions and reusable pipeline actions (`helm/rudder@v1`, `helm/package@v1`, `go/build`). It builds on standard **Debian and Alpine** foundations — not Chainguard's Wolfi undistro — but delivers the same distroless, non-root, near-zero-CVE, SBOM + SLSA L3 provenance + OpenVEX + cosign-signed properties.
- For the four job responsibilities, the concrete toolchain is: **(1) Helm adaptation** → Docker's `helm/rudder` action + values overrides/securityContext hardening + `-helm`/`-compat` image variants + `regctl` for OCI mirroring; **(2) version tracking** → Renovate is the industry standard for tracking hundreds of upstreams/monorepos at scale (Docker pins every upstream by git commit + SHA256 digest); **(3) Go K8s integration testing** → Ginkgo/Gomega, kind, `sigs.k8s.io/e2e-framework`, controller-runtime envtest, Terratest, kuttl, and chart-testing (`ct`); **(4) CVE triage** → Docker Scout (Docker's own product, built from the Atomist acquisition), Trivy, Grype, Syft, OpenVEX + `vexctl`, EPSS/KEV scoring.
- DHI launched **May 19, 2025** as a paid add-on and was made **free and fully open-source under Apache 2.0 on December 17, 2025** — "its catalog of more than 1,000 Docker Hardened Images (DHI), built on the widely adopted open source distributions Debian and Alpine." It is a direct competitor to Chainguard; the two companies now publicly spar over build methodology (Chainguard builds everything from source on its own Wolfi/Chainguard OS; Docker hardens Debian/Alpine).

## Key Findings

### DHI product background
- **Launch timeline:** Docker announced DHI on **May 19, 2025** (press release "Docker Announces Hardened Images Catalog") as a commercial, paywalled add-on for Pro/Team/Business plans. On **December 17, 2025**, Docker made the entire catalog free and open-source under **Apache 2.0**, keeping paid **DHI Select** and **DHI Enterprise** tiers plus a **DHI Extended Lifecycle Support (ELS)** add-on.
- **Tiers:** *Community* (free, Apache 2.0 — full catalog, near-zero CVEs, SBOMs, SLSA Build L3 provenance, OpenVEX, signatures); *Select* (adds SLA-backed CVE remediation, FIPS-validated + STIG-aligned variants, limited customization); *Enterprise* (unlimited customization, access to Docker Hardened System Packages repo, ELS eligibility). Per Docker's Dec 17, 2025 press release, DHI Enterprise delivers "SLA-backed CVE remediation for critical vulnerabilities in under seven days, with a roadmap toward a 24-hour SLA" (BleepingComputer, Dec 18, 2025, notes the 7-day SLA is exclusive to the commercial Enterprise tier). ELS "provides: Five additional years of security coverage beyond upstream end-of-life · Continued CVE patches, SBOM updates, and provenance attestations."
- **Foundations:** Built on **Debian and Alpine** (both glibc and musl variants), explicitly positioned as a "drop-in" that requires changing one Dockerfile line, versus proprietary distros. Distroless runtime, non-root by default. Per the Dec 17, 2025 press release: "Docker Hardened Images reduce vulnerabilities by up-to 95 percent compared to traditional community images. They use a distroless runtime to minimize the attack surface." Docker frames the urgency by citing Cybersecurity Ventures: "Supply chain attacks are projected to cost businesses $60 billion globally in 2025."
- **Relationship to Chainguard:** Docker and Chainguard partnered in March 2024 (Chainguard joined Docker's Verified Publisher program). DHI is now a direct competitor. Chainguard's public comparison notes the core methodological difference: Chainguard builds every package from source on its own OS (Wolfi/Chainguard OS), while "Docker Hardened Images builds some packages from source while incorporating others from prebuilt archives." Docker counters that being Debian/Alpine-based means no proprietary lock-in.
- **Consumption:** Images pulled from `dhi.io/<image>:<tag>` (login required); mirrored to your own Docker Hub namespace or third-party registry with `regctl`; consumed in Dockerfiles (multi-stage: `-dev` build stage + minimal runtime), and via Helm charts (`dhi.io/<name>-chart`, OCI artifacts). Docker's blog "Docker Hardened Images: Security Independently Validated by SRLabs" reports the outcome of a grey-box review: "After three weeks of targeted testing, including adversarial modeling and architectural probing, SRLabs came back with a clear message: no critical vulnerabilities, no high-severity exploitation paths, just a medium residual risk driven by industry-wide challenges like key stewardship and upstream trust." SRLabs recommended HSM-backed signing keys and a move toward keyless Fulcio flow, which Docker says it has started.

### The DHI internal build system (the core discovery)
Primary-source evidence from the open catalog repo, verified by fetching the actual YAML at commit `8c07ac4f`:
- **`dhi.io/build` is a custom BuildKit frontend, self-hosting.** Every definition file starts with `# syntax=dhi.io/build:2-debian13` (a BuildKit syntax directive). The build binary `dhi-build` is compiled from Go source cloned from `github.com/docker-hardened-images/frontend` (e.g. `#v2.4.3`), and the build image declares BuildKit frontend capabilities via labels (`moby.buildkit.frontend.caps`, `moby.buildkit.frontend.network.none: "true"`). The system builds itself and all other catalog images. **There is zero reference to apko or melange anywhere in the repo.**
- **This is the biggest correction to the common assumption.** DHI is *not* a Chainguard apko/melange/Wolfi derivative. It is Docker's own declarative, BuildKit-native build system operating on Debian (`apt`) and Alpine (`apk`) packages, with `DHI_BUILD_TYPE` set to `debian`, `alpine`, or `source`.
- **Definition-file structure:** YAML files under `image/`, `chart/`, `package/`. Key fields: `contents` (with `packages` include/exclude lists where `!` prefixes exclusions, and `builds` for multi-stage), `files` (source acquisition via `url: git+https://...` + `checksum:`), `pipeline` (steps with `runs:` shell or `uses:`/`with:` actions), `outputs` (source→target with uid/gid/mode), `accounts` (defines `nonroot` UID/GID 65532 for runtime, `run-as: root` for dev variants), `spdx` (SBOM metadata with PURLs), `platforms` (linux/amd64, linux/arm64).
- **Reusable pipeline actions** (primary-verified): `helm/rudder@v1`, `helm/cmd@v1`, `helm/package@v1`, `go/build`. Secondary (DeepWiki, not primary-verified): `yq/patch@v1`, `npm/bump@v1`.
- **Naming convention:** `dhi.io/{application}:{semver}-{os}{os-version}[-{variant}]@sha256:{digest}`. Variants: **`dev`** (build-time, root, package managers + build tools), **runtime** (no suffix, nonroot UID 65532, minimal), **`compat`** (extended runtime with extra packages for legacy/Helm compatibility), **`source`** (with source-inspection tools like `dhi-source`), **`helm`** (Helm chart packaging), **`fips`** (FIPS-140-validated crypto, paid tiers only).
- **Continuous rebuilds:** Docker describes an **"event-driven build system"** that "scans tens of thousands of CVE notifications across the ecosystem" and automatically rebuilds from source whenever upstream fixes appear. Digest-pinning is used everywhere (all base images and artifacts by `@sha256:`, git sources by `checksum:`).
- **Signing/provenance:** SLSA Build Level 3 provenance, signed SBOMs (SPDX + CycloneDX), OpenVEX exploitability data, cosign/Sigstore signatures — attached as OCI attestations, verifiable via `docker scout attest` or `cosign`.

## Details by Responsibility Area

### 1. Helm chart adaptation for DHI (cert-manager, grafana, mongodb, kyverno, etc.)

**What Docker actually uses (primary-source):**
- **The build pipeline for charts** lives in `chart/<name>/helm/*.yaml` and uses Docker's own **`helm/rudder@v1`** action with two commands: `prepare` (injects DHI image references — pinned by SHA256 digest — into the chart) and `patch` (applies overrides from the chart's `config/` directory). Then `helm/cmd@v1` runs `lint`, and `helm/package@v1` packages the chart. Charts are published as OCI artifacts to `dhi.io/<name>-chart`.
- **values.yaml override mechanism:** Docker's `config/values.yaml` uses template variables like `${clickhouse-operator.registry}/${clickhouse-operator.repository}` and `${...tag}@${...digest}` that `helm/rudder patch` resolves to the pinned hardened images. This is the concrete "image swapping" technique. Security context is hardened directly in these overrides, e.g. `runAsNonRoot: true`, `runAsUser: 65532`, `runAsGroup: 65532`.
- **The `-helm` / `-compat` image variants exist specifically to solve chart compatibility.** Upstream charts often assume a shell, entrypoint scripts, `gosu`/`su-exec`, or chown steps that a distroless runtime lacks. Docker ships a `-helm`-flavored image line for exactly this — e.g. the Vault chart is "wired to the `-helm` image line by default … That image includes additional tools so the upstream templates (shell snippets, entrypoint script paths) work." Using the minimal runtime tag instead would break the chart.
- **Consumption/mirroring:** Because DHI charts reference images in private repos, users mirror with **`regctl image copy … --referrers`** (charts are OCI artifacts), then re-point image references via **pre-rendering** (a values override file) or **post-rendering** (a script that rewrites `dhi/` or `docker.io/dhi/` prefixes after Helm templating). A `kubectl create secret docker-registry` pull secret is required per namespace.
- **Status:** Helm charts in the DHI catalog went to **invite-only beta in October 2025** and were open-sourced with the December 2025 launch. The catalog `chart/` directory includes cert-manager, grafana-agent/alloy, vault, traefik, minio, velero, redis, valkey, etcd, kube-prometheus-stack, kyverno, and more.

**The general hardening techniques the role requires (industry-standard, and what the DHI charts encode):**
- Pod/container **`securityContext`**: `runAsNonRoot: true`, non-root `runAsUser`/`runAsGroup`/`fsGroup`, `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`, `capabilities: drop: [ALL]`, `seccompProfile: RuntimeDefault` (Kubernetes "restricted" Pod Security Standard).
- Handling `readOnlyRootFilesystem` by mounting writable `emptyDir` volumes for `/tmp` and cache paths.
- **Known upstream friction points:** cert-manager historically applied `readOnlyRootFilesystem` at the pod `securityContext` level (invalid — it's a container-level field), and moved controller/webhook/cainjector pods to `runAsNonRoot: true` to pass the Kyverno restricted policy. This is exactly the class of major-version-break/compatibility work the role describes.
- Supporting tools commonly paired: `kustomize`, `helm-unittest`, `kubeconform`, `conftest`/OPA, Kyverno/Gatekeeper admission policies.

### 2. Version tracking / upstream release tracking across many repos and monorepos

**How DHI does it (primary-source):** Every DHI definition pins upstream by **git ref + commit checksum** (e.g. `git+https://github.com/grafana/alloy.git#helm-chart/1.6.0` with a pinned `checksum:`) and every base image/artifact by **`@sha256:` digest**. Version variables in the `vars` block support regex extraction (e.g. `${VERSION:^v?([0-9]+).*$}`) to derive semver-based tags. When upstream releases, the definition's pins are bumped and the event-driven build system rebuilds.

**Industry-standard tooling for tracking hundreds of upstreams at scale (what a role like this uses/prepares for):**
- **Renovate is the clear winner for monorepos and multi-repo fleets at scale.** It offers workspace-aware discovery, `group:monorepos` presets, shared org-wide config presets (one `extends` line rolls policy to every repo), a Dependency Dashboard, fine-grained scheduling, and 90+ package managers across GitHub/GitLab/Bitbucket/Azure DevOps. It is designed to reduce PR-fatigue — one team cut ~200 Dependabot PRs/week to a manageable grouped set, saving ~15 hours/month.
- **Dependabot** is the zero-config GitHub-native fallback; good for security alerts, weaker for large monorepos (per-directory config, one-PR-per-dependency).
- **Renovate specifically tracks container image tags and Helm chart versions**, not just language deps — directly relevant to DHI work. It can also auto-detect and respect Helm chart dependency updates.
- Complementary release-tracking: **release-please** (release automation from conventional commits), custom bots, and for major-version-break/dependency-chain management, Renovate's grouping + the Dependency Dashboard to stage majors behind checkbox approval.

### 3. Go-based Kubernetes integration testing

The role's description maps directly onto the standard Go/K8s testing stack. Concrete tools, with where each fits:
- **Ginkgo (v2) + Gomega** — the BDD test framework + matcher library that underpins Kubernetes' own `test/e2e`. `Describe/Context/It/BeforeEach/AfterEach`, `Eventually`/`Consistently` for polling assertions. This is the backbone of nearly all in-cluster Go testing.
- **kind (Kubernetes in Docker)** — the de-facto ephemeral cluster for CI; `helm/kind-action` spins one up in GitHub Actions. This is where "real Kubernetes environment" tests actually run.
- **`sigs.k8s.io/e2e-framework`** — the modern, modular provider-independent E2E framework (successor patterns to `k8s.io/kubernetes/test/e2e/framework`), designed to be usable outside core Kubernetes for testing images/charts/controllers.
- **controller-runtime envtest** — spins up a local API server + etcd (no full cluster) for fast controller/CRD integration tests; standard in Kubebuilder-scaffolded projects.
- **Terratest** — Go library (`gruntwork-io/terratest/modules/helm` + `/k8s`) to `helm install`/`helm template`, deploy to a cluster, wait for readiness, and assert on live resources; also supports render-and-assert unit testing of charts by unmarshalling rendered YAML into typed K8s API structs. Strong fit for validating that a hardened chart still renders the expected securityContext, image refs, probes, etc.
- **kuttl (KUTTL)** — declarative, YAML-based integration harness; can `startKIND: true`, install a Helm chart in a `TestStep`/`TestSuite`, and assert on resulting object state. No Go code required, good for chart install/upgrade validation.
- **chart-testing (`ct`)** — the Helm project's official tool for lint + install + upgrade testing of changed charts against a kind cluster; `ct lint`, `ct install --upgrade`, change detection via `ct list-changed`. This is the canonical CI gate for Helm chart repos.
- **helm test hooks**, **helm-unittest**, **kubeconform**, **Testcontainers-Go**, and Guidewire's **Sawchain** (Chainsaw-powered Go library) round out the ecosystem.

For DHI specifically, the catalog's image definitions include a **`tests` section** for "automated validation and compliance checks," and Docker recommends validating minimal/distroless image behavior **via CI pipelines rather than interactive inspection** (since there's no shell). The exact Go framework Docker uses internally is not publicly documented, but the catalog repo is 67.5% Shell / 15.9% Python / 11.7% Makefile, and the industry norm for the in-cluster Go validation the role describes is Ginkgo/Gomega + kind + e2e-framework/Terratest.

### 4. CVE triage and security hardening

**Docker's own stack:**
- **Docker Scout** is Docker's vulnerability/supply-chain product and the native way DHI's attestations are consumed. It grew out of Docker's **acquisition of Atomist** — as Docker Senior Principal Engineer Christian Dupuis put it (Dec 17, 2025 blog), "from the early days at Atomist building an event-driven SBOM and vulnerability management system, the foundation that still underpins Docker Scout today." Scout cross-references SBOMs against multiple CVE databases (NVD, GitHub Security Advisories), supports **EPSS** scoring (`docker scout cves --epss`) for exploitation-probability prioritization, reads OCI VEX attestations automatically, and verifies attestations natively (`docker scout attest list/get`, `--verify`).
- **VEX / OpenVEX workflow:** DHI ships **signed OpenVEX** exploitability statements as OCI attestations. Docker publishes DHI VEX through two channels: the OCI attestation (read automatically by Docker Scout, and by Trivy/Grype/Wiz) and a public advisories repo (`github.com/docker-hardened-images/advisories`) that **Trivy** can consume via `trivy vex repo`. Engineers author/attach their own VEX with **`vexctl`** and **`docker scout attestation add --predicate-type https://openvex.dev/ns/...`**. The **Sysdig integration** for Docker Scout auto-generates VEX from runtime package-loading data.
- **SBOMs:** signed SPDX + CycloneDX per image, generated by the build system; **Syft** is the standard external generator.
- **Transparency stance:** Docker deliberately shows unfixed CVEs (no suppressed feeds), contrasting with vendors who "suppress CVEs to maintain a green scanner." Docker states it "uses DHI internally to build this vulnerability management model," with policy-driven assessment, VEX attestations, and auditable decisions.

**The broader triage stack the role uses:**
- **Trivy** (Aqua) — the dominant all-in-one scanner: OS + language CVEs, IaC, secrets, licenses, K8s clusters, Helm charts, SBOM gen/consume, native VEX support. Best single-tool CI gate (`trivy image --severity HIGH,CRITICAL --exit-code 1`).
- **Grype** (Anchore) + **Syft** — the SBOM-first pairing; Grype is ~30–40% faster for pure vuln scanning and adds **EPSS + CISA KEV composite scoring** for prioritization. Common 2026 pattern: generate one Syft SBOM, gate with Trivy, second-opinion with Grype on critical images (independent DBs widen coverage).
- **Patch backporting:** In the DHI model this happens by rebuilding the affected package from source in the definition (bumping the pinned commit/version) — analogous to how Wolfi/melange package definitions are patched, but implemented in Docker's own frontend rather than melange. Enterprise tier exposes the **Docker Hardened System Packages** repo (apk/apt repos at `dhi.io/apk/...` and `dhi.io/deb/...`, signed with DHI keys) so customers install the same Docker-patched, source-built packages in custom images.
- **Debugging distroless images** (since triage often needs it): **Docker Debug** or `kubectl debug`/ephemeral containers with a `busybox`/`wolfi-base` sidecar, since DHI runtime images have no shell.

## Recommendations

**To prepare for or replicate this DHI role, in staged order:**

1. **Master the DHI build model first.** Clone `github.com/docker-hardened-images/catalog`, read the `image/`, `chart/`, and `package/` YAML, and internalize that the build system is Docker's own **`dhi.io/build` BuildKit frontend** (not apko/melange). Understand the declarative `contents`/`builds`/`pipeline`/`outputs`/`accounts` schema, the `helm/rudder`/`helm/package` actions, the variant taxonomy (`dev`/runtime/`compat`/`helm`/`source`/`fips`), and digest-pinning. *Benchmark to advance:* you can trace how a single upstream version bump flows from a pinned git commit → rebuilt package → new image tag → chart image swap.

2. **Build hands-on Helm-adaptation muscle.** Take an upstream chart (cert-manager, grafana, kyverno) and (a) swap images to DHI equivalents via values overrides, (b) add restricted-PSS `securityContext` (nonroot 65532, `readOnlyRootFilesystem`, dropped caps, seccomp), (c) add writable `emptyDir` mounts for `/tmp`, and (d) resolve the shell/entrypoint/`gosu` breakages that force use of `-helm`/`-compat` variants. Practice `regctl` mirroring and pre-/post-render image re-pointing. *Threshold:* the chart installs and passes `helm test` on a kind cluster with runtime (non-dev) images.

3. **Stand up the version-tracking automation.** Deploy **Renovate** (self-hosted or app) across a multi-repo/monorepo test estate with shared presets, monorepo grouping, container-image and Helm datasources, and the Dependency Dashboard for staging major-version breaks. Know when Dependabot suffices vs. when Renovate is required (multi-platform, monorepo, hundreds of upstreams → Renovate). *Threshold:* a new upstream release opens a grouped, correctly-scoped PR with the digest updated.

4. **Build the Go integration-test harness.** Write Ginkgo/Gomega suites that deploy to a **kind** cluster (via `sigs.k8s.io/e2e-framework` or Terratest's `helm`/`k8s` modules), assert pods run as nonroot with the expected securityContext, and validate chart upgrade paths. Add **chart-testing (`ct`)** and **kuttl** as CI gates. *Threshold:* CI fails automatically when a chart change weakens a security control or breaks install/upgrade.

5. **Operationalize CVE triage.** Wire **Docker Scout** + **Trivy** (with the DHI VEX repo) + **Grype/Syft** into CI; consume DHI OpenVEX attestations; author exceptions with **`vexctl`**/`docker scout attestation add`; prioritize with **EPSS/KEV**. *Threshold:* post-VEX scans show near-zero actionable findings and every remaining CVE decision is documented as a signed VEX statement traveling with the artifact.

**Signals that would change the approach:** If Docker publishes an official "how DHI is built" engineering deep-dive or open-sources the `frontend` repo internals, prioritize that over inferred structure. If the FIPS/STIG or ELS requirements dominate your target org, weight the Enterprise-tier package repo and compliance-variant workflow more heavily. If your estate is GitHub-only and small, Dependabot may be sufficient over Renovate.

## Caveats
- **What Docker officially documents:** the DHI product (tiers, Debian/Alpine base, distroless/non-root, SBOM/SLSA-L3/OpenVEX/cosign, event-driven rebuilds, 7-day CVE SLA), the Helm chart consumption/mirroring workflow, Docker Scout + VEX tooling, and the open catalog repo with its YAML definitions and `helm/rudder`-style actions.
- **What is strongly implied / secondary-sourced:** the internal `dhi.io/build` frontend being a self-hosting BuildKit frontend compiled from `docker-hardened-images/frontend` is verified from the actual catalog YAML at commit `8c07ac4f`, but Docker has not published a formal architecture doc. The DeepWiki analysis corroborates it but is AI-generated; the pipeline actions `yq/patch@v1` and `npm/bump@v1` and the exact `compat`/`source` variant semantics rest partly on that secondary source. Chainguard's characterization that Docker "incorporates others from prebuilt archives" is a competitor's claim.
- **What is industry-standard-but-unconfirmed for Docker specifically:** the exact Go integration-testing framework Docker uses internally (Ginkgo/Gomega + kind + e2e-framework/Terratest is the norm and matches the job description, but Docker hasn't published its internal suite), and whether Docker uses Renovate/Dependabot internally (they pin by git commit + digest; the automation tool is not disclosed — Renovate is the standard for this scale).
- **DHI is emphatically not Wolfi/apko/melange-based** despite widespread assumptions in secondary blog posts; several third-party guides conflate DHI with Chainguard's toolchain. The migration guide even shows migrating *from* Wolfi/Chainguard *to* DHI. Treat any source claiming DHI "is built with apko/melange" as inaccurate.
- Some cited figures ("up-to 95 percent" attack-surface reduction, the "$60 billion" supply-chain cost, "five additional years" ELS) are Docker press-release or third-party (Cybersecurity Ventures) claims, not independently audited.
- Pricing for Select/Enterprise is not publicly disclosed; a Docker login is required to pull from `dhi.io`, and some debugging (Docker Debug) requires a Docker Desktop subscription.
