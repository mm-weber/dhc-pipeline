# `grafana-13.0.4.linux-amd64.tar.gz` no longer matches its published `.sha256`

## Summary

The `linux-amd64` release tarball for **13.0.4** was modified on
**2026-07-22**, about 17 hours after the 13.0.4 release was published, but the
`.sha256` file served alongside it was **not** regenerated. It still advertises
the pre-modification digest.

The result is that `dl.grafana.com` currently serves an artifact that its own
published checksum disowns:

| | SHA-256 |
|---|---|
| `grafana-13.0.4.linux-amd64.tar.gz` (actual bytes) | `54eceec74891dd49f992502eab506e0554c82903317fb50d82246946e46fe7ae` |
| `grafana-13.0.4.linux-amd64.tar.gz.sha256` (published) | `cd8c8b31b0482f48f98018030c142919dab6debbe81f747f3521af6f6a6b4490` |

Anyone who verifies the download against the published checksum — which the
checksum file exists to enable — now gets a hard failure. Anyone who does not
verify silently receives different bytes than the release originally shipped,
with no change in the version string to signal it.

## Reproduction

```console
$ curl -sSL https://dl.grafana.com/oss/release/grafana-13.0.4.linux-amd64.tar.gz \
    | sha256sum
54eceec74891dd49f992502eab506e0554c82903317fb50d82246946e46fe7ae  -

$ curl -sSL https://dl.grafana.com/oss/release/grafana-13.0.4.linux-amd64.tar.gz.sha256
cd8c8b31b0482f48f98018030c142919dab6debbe81f747f3521af6f6a6b4490
```

| `grafana-13.0.4.linux-amd64.tar.gz` | `54eceec7…` | `cd8c8b31…` | ❌ |
| `grafana-13.0.4.linux-arm64.tar.gz` | `591ac184…` | `591ac184…` | ✅ |

arm64 is self-consistent, so this is not a blanket failure of checksum
generation.

### A second observation we cannot fully explain

We also saw the **same URL verify and then fail within the same hour**, on a
different version. Two CI builds, identical pinned digest, identical URL:

| Time (UTC) | Downloaded | Verified against `0c071169…` (13.1.1's published sidecar) |
|---|---|---|
| 2026-07-26 21:06 | `grafana-13.1.1.linux-amd64.tar.gz` | ✅ passed |
| 2026-07-26 21:54 | `grafana-13.1.1.linux-amd64.tar.gz` | ❌ failed |

We are explicitly **not** claiming this is the same defect. Two explanations fit
and we cannot distinguish them from outside your infrastructure:

1. `dl.grafana.com` serves inconsistent bytes for one URL — e.g. edge nodes
   holding different copies during or after a re-upload.
2. Transport-level corruption or truncation on our side, which would be our
   problem and not yours.

The 13.0.4 finding above is independent of this and does not rely on it: that
one was measured with a plain `curl | sha256sum` from a workstation, not in CI.

If you have a way to check whether all edges serve identical bytes for a given
release object, that would settle which explanation applies.

## Timeline

| When (UTC) | What |
|---|---|
| 2026-07-21 10:21 | v13.0.4 tag created |
| 2026-07-21 12:25 | v13.0.4 release published (part of a coordinated security release alongside v13.1.1, v12.4.6, v12.3.9) |
| **2026-07-22 05:36** | **`grafana-13.0.4.linux-amd64.tar.gz` last modified** |

The modification falls the day *after* a coordinated multi-branch security
release, which is consistent with a corrective re-upload during that window.

## Why this matters downstream

We hit this in an image build pipeline that pins upstream artifacts by SHA-256
and verifies them at fetch time. The build had been reproducible against
13.0.4; it now fails at the verification step, because the pinned digest — which
still matches your published `.sha256` — no longer matches the bytes served.

More generally, for anyone consuming these tarballs:

- **Verifying consumers break.** Package managers, image builds, Bazel/Nix-style
  pinned fetches, and anything using the `.sha256` will fail on a version that
  previously worked, with no version change to explain it.
- **Non-verifying consumers are worse off.** They receive different bytes than
  the release advertised and have no signal that anything changed.
- **Reproducibility is lost for 13.0.4.** There is currently no way to obtain the
  artifact the release originally shipped, and no published record of what
  changed between the two.

We deliberately did **not** re-pin to the new digest, since that would mean
shipping bytes that fail your own published verification.

## Questions

1. **Which artifact is authoritative** — the one currently served
   (`54eceec7…`), or the one the `.sha256` describes (`cd8c8b31…`)?
2. If the re-upload was intentional, could the **`.sha256` be regenerated** so
   the pair is consistent again?
3. Were **other artifacts modified in the same window** (other architectures,
   other formats, or the 12.4.6 / 12.3.9 / 13.1.1 branches from the same
   release batch)? A sweep of objects with a `last-modified` after their release
   date would confirm the blast radius.
4. Do all CDN edges serve **identical bytes** for a given release object? This
   would settle the second observation above.
4. Is there a **changelog or rationale** for what differed between the two
   builds? For consumers who already shipped the original artifact, knowing
   whether the change was cosmetic (packaging) or substantive (binary content)
   determines whether they need to rebuild.

## Suggestion

Two things would prevent recurrence, independent of what caused this one:

- **Treat release artifacts as immutable.** If a build needs correcting, publish
  it under a new version (as was already done for `+security-NN` builds) rather
  than replacing bytes behind an existing version URL.
- **Regenerate the sidecar in the same operation that writes the artifact**, so
  the two cannot drift apart even if a replacement does happen.

Happy to provide any further detail or re-run the checks if useful. The 13.0.4
measurement is reproducible with the two commands above; the intermittent
behaviour is, by nature, not.
