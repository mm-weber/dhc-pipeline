## Findings

**r1.1 Floating builder references outside the lint's keys pass (1.2, 1.6). Severity: medium.**
- **What the sentences say:** every base image reference is pinned by sha256 (1.2), and a floating tag in a definition fails validation naming it (1.6).
- **What the code does:** lint-pins.sh:70-76 extracts only lines keyed `image:`, `base:` or `uses:`. For `uses:` it skips any value without a "/" or whose first segment has no dot (lint-pins.sh:61-65). That rule exists to skip frontend actions (`go/build@v1`), but it also skips a Docker Hub image at builds level.
- **Probes (exit 0, "all pinning conventions satisfied"):** `uses: golang:1.25-alpine`, `uses: library/golang:1.25-alpine`, `GOLANG_REFERENCE: dhi.io/golang:1.27`. Control: `uses: dhi.io/golang:1.27` exits 1, named.
- **What keeps it safe today:** Renovate's docker manager (renovate.json5:84-88), which only matches a pinned `dhi.io/...@sha256`.
- **Who is affected:** a release built from a mutable builder tag after an unreviewed slip. Its content can change between builds with no red check.

**r1.2 Source-pin shape is not checked before merge (1.3). Severity: medium.**
- **What the sentence says:** a git ref plus commit checksum, or a versioned URL plus per-arch checksum.
- **What the code does:** lint-pins.sh:117-123 only compares the count of `git+` lines with the count of `checksum:` lines anywhere in the file.
- **Probes (exit 0):** a `git+` url with no `#ref`; `checksum: main` (not a hash); grafana with its `GRAFANA_SHA256` var removed. verify-arch-pins.sh:59-62 then reports "nothing to verify" and exits 0, so a repackage definition with no per-arch pin and no `sha256sum -c` step passes every PR check.
- **When it is caught:** only by the daily check-authenticity.sh (:98 "no git+ source ref", :122 "no per-architecture pinned tarball"). That runs after main has built, signed and tagged, and only for active definitions.
- **Who is affected:** a release can ship before the rescan flags it.

**r1.3 Flow-style package repositories skip the /main check (1.12). Severity: medium.**
- **What the code does:** the awk at lint-pins.sh:165-173 starts reading only on a line that is exactly `repositories:`. A flow list `repositories: [https://dhi.io/apk/alpine/v3.23/security, ...]` exits 0 (probed).
- **Contrast:** lint-pins.sh:193-196 refuses flow style for `vars:` and `tags:` for exactly this reason, but not for `repositories:`.
- **Who is affected:** an entitlement-gated repository could enter a definition silently. The manual's own anatomy writes repositories in flow style (r1.11).

**r1.4 Validate's fail-validation steps are skipped when an earlier step fails (1.6, 1.11, 1.12, 1.16, 1.18). Severity: medium.**
- **What the code does:** the conventions job (validate.yml:12-342) is one sequential job with no `if: always()`. lint-pins.sh is step 5 (:42-43), after yamllint, the chart pins and compat step, and the revocation schema. lint-active-set.sh is step 14 (:122-134). Any earlier red step leaves a floating tag, a `none` class, an off-/main repository, an inactive bump or a group split unnamed. The job is still red, so merge stays blocked by the required check "yamllint, pin lint, policy tests" (.github/rulesets/main_sec.json:45).
- **Seen live:** triage/LOG.md:3844, PR #354: validation stopped before the active-set step.
- **About to recur:** chart/valkey/chart.yaml:50 sets `review_by: 2026-11-24`, and lint-compat.sh:105-107 fails from 2026-11-25. From then every pull request's validate stops at step 3 until a re-decision lands, and no Req 1 lint runs.
- **The repository already has the remedy elsewhere:** the rescan enforces always() on its steps (lint-rescan-steps.sh).

**r1.5 The frontend's identity is not checked (1.7). Severity: low.**
- **What the code does:** lint-pins.sh:79-92 demands a digest-pinned `# syntax=` line on line 1 but accepts any frontend name. Renovate tracks only `dhi.io/...` (renovate.json5:85).
- **Effect:** a definition for another frontend would pass lint, build, and go untracked. Nothing ties a definition to the backend that the 9.15 table (user-manual.md:1623) names. Held by review only.

**r1.6 Document: "floating tags fail CI" / "every image reference" (1.6). Severity: low.**

- **The code that contradicts them:** lint-pins.sh:61-65 and :70 (keys image/base/uses only, short-form `uses:` skipped). The probes are in r1.1.

**r1.7 Document: CONVENTIONS' pin rules and their gate (1.3). Severity: low.**
- **The claims:** docs/CONVENTIONS.md:143-145 says each rule is held by lint-pins.sh "unless another is named". :162 says "Every `git+` source line has a sibling `checksum:` (commit hash)". :163-171 gives the tarball rule.
- **What the code does:**
  - lint-pins.sh:117-123 counts lines. It checks neither the sibling position nor the hash form.
  - lint-pins.sh does not read the tarball rule at all, and verify-arch-pins.sh:59-62 skips silently when the pin is absent.
- **A second error in the same rule:** CONVENTIONS.md:164 gives the tarball URL shape as `https://…/<name>-<ver>.linux-${ARCH}.tar.gz`. That is the rewritten alias shape the grafana definition explicitly rejects (image/grafana/image.yaml:22-32; it pins the per-build `grafana_<ver>_<build-id>_linux_${target.arch}.tar.gz`, :59). Someone onboarding from this rule copies the shape that moved under the repository in July.

**r1.9 Document: the builder contract says downstream never reads a definition (1.17). Severity: low.**
- **The claim:** docs/user-manual.md:1601-1609 says "Downstream reads outputs only, already true by construction ... None of them reads a definition to learn about an image."
- **What the code does:** downstream planes do read definitions:
  - compile-vex.sh:79-81 reads image/<def>/image.yaml for the published repository;
  - enumerate-catalogue.sh:10-11 and :25-26 take repositories and supported tags from the definitions;
  - scan-image.sh:53 keys the exception file by definition;
  - rescan.yml:814-824 builds the page's definition list from them;
  - check-inactive-digests.sh reads declared tags.
- **Who is affected:** a fork swapping the backend. The contract's input must keep `image:` and `tags:` readable to those planes, and the contract does not say so.

**r1.10 Document: the manual's validate battery and requirements map omit the Req 1 lints. Severity: low.**
- **The claims:** docs/user-manual.md:323-336 lists the conventions job "in order" without lint-accounts.sh, lint-active-set.sh or render-tracking.sh --check, and its order is not the code's. docs/user-manual.md:1727 maps Req 1 to lint-pins.sh, the frontend compile and verify-arch-pins.sh only.
- **What the code has:** validate.yml:63-64 (1.4), :122-134 (1.16, 1.18, 1.19), :139-140 (1.14), plus check-inactive-digests.sh in the rescan (1.15).

**r1.11 Document: the anatomy sketches use flow style the lints treat differently. Severity: low.**
- **The sketches:** docs/user-manual.md:1155 (`tags: [...]`) and :1163 (`repositories: [https://dhi.io/apk/…]`); .specs/dhc-catalogue-mvp/design.md:1677 (`repositories: [https://dhi.io/apk/alpine/v3.23/main, …]`).
- **How the lint reacts:** flow-style `tags:` is refused by lint-pins.sh:193-196 (probed, exit 1). Flow-style `repositories:` is not read by the 1.12 check (r1.3).
- **Effect:** a reader copying the "Add an image definition" anatomy gets a red lint for the tags and an unchecked repository list.
