## Findings

**r5.1: A chart in the harness but not in componentSpecs passes e2e with nothing installed (Req 5.2). Severity: high, latent.**
- *What the sentence says:* each affected chart deploying an active definition is installed on kind.
- *What the code does:*
  - The matrix comes from chart/*/chart.yaml deploys: against the active set (e2e.yml:58, definition-lib.sh:156-170).
  - TestMain resolves --chart through harness.Lookup and exits 1 on an unknown name (e2e_suite_test.go:63-67). The registry is test/harness/harness.go:21-26.
  - The specs iterate a second, hand-kept list, componentSpecs (test/e2e/components_test.go:25-48). It carries the selector and the replica count.
  - Every Context skips when selected.Name != s.Name (components_test.go:58-59; upgrade_test.go:33-34).
  - So a component present in harness.Components and absent from componentSpecs runs zero specs. Ginkgo reports skipped specs as a pass, so go test exits 0, the leg is green and the e2e gate is green (e2e.yml:291-293).
  - No test compares componentSpecs with harness.Components or with chart/*/chart.yaml. harness_test.go:11 TestComponentsRegistry checks the registry alone; TestProbeDeclarations checks probes only.
- *Who is affected:* the owner and a fork. The first chart PR of an onboarding is the one PR whose kind run is the image's first live proof (Decision 14). It would merge on a green gate that installed nothing, and the image would be published and pinned with no live securityContext or probe check.
- *Reachability:* not reachable on the reference's four charts, which are in both lists. Reachable by following the documented onboarding steps (r5.4).

**r5.2: The none-proof report is not printed in every validation run (Req 5.9). Severity: medium.**
- *What the sentence says:* the CI pipeline reports each kind-none declaration by name with its reason in every validation run. design.md:1706, user-manual.md:451 and :1668 say "on every run".
- *What the code does, case 1 (skipped step):* the report is a line of lint-probes.sh (:99). The script runs as step 17 of validate's conventions job (validate.yml:147-148), with GitHub's default success() condition. Any earlier failing step skips it: yamllint, lychee, kyverno tests, the active-set lint and the others at validate.yml:22-145. A red run for an unrelated cause then shows no declared gap.
- *Case 2 (malformed input):* a malformed proofs map or active set prints nothing but the refusal (lint-probes.sh:48-57). The run is red, but the valid none entries are not reported.
- *Case 3 (multi-line reason):* proof_entries emits one tab-separated line per entry (definition-lib.sh:220-221), and the lint reads it line by line (lint-probes.sh:61-64). A multi-line reason (YAML |) is reported only up to its first newline.
  - Probed: `reason: |\n first line\n second line` printed "lint-probes: valkey: proof none, first line (Req 5.9)".
- *Who is affected:* the owner's view of declared gaps.
- *Today:* vacuous, because proofs: {} (catalogue-policy.yaml:111). The clause applies at the next onboarding.

**r5.3: A skipped lint step fails validation without naming the definition or entry (Req 5.8, 5.10). Severity: low.**
- *What the sentences say:* "fail validation naming that definition" (5.8) and "naming that entry" (5.10).
- *What the code does, skipped step:* when an earlier conventions step fails, lint-probes.sh (validate.yml:147) is skipped. Validation still fails, but the run names neither the definition nor the entry; the name appears only once the earlier cause is fixed.
- *Unregistered probe:* the YAML lint counts a chart's probe: as covering its definitions whether or not the name is registered (lint-probes.sh:77-79,107-110). The Go half fails instead (probes_registry_test.go:42-44, validate.yml:395-397) and names the chart file and the probe, not the definition.
- *Who is affected:* the owner, who gets a red run with the cause one step removed. No release or consumer is affected.

**r5.5 (document): The "harness change smoke-tests" rule does not cover the module files. Severity: low.**
- *Claims:* user-manual.md:422 says "a change to the harness itself smoke-tests on hardened-app". docs/lanes.md:427 says "a harness change adds the simplest one".
- *What the code does:* e2e.yml:89 matches only `^\.github/workflows/e2e\.yml$|^test/(e2e|checks|install|harness)/`. A PR changing only test/go.mod or test/go.sum (a Renovate gomod bump of e2e-framework, ginkgo or the k8s client libraries) runs no e2e leg. It gets only compile, vet and unit tests (validate.yml:360-397).
- *Who is affected:* the suite's own dependencies can change on main without one live run. Nothing in Req 5's text demands that run, so this is a document finding against the stated rule, not a criterion gap.

**r5.6 (document): design.md says e2e-framework provisions kind; in CI the workflow does. Severity: low.**
