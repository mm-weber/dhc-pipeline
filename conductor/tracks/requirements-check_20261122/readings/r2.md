## Findings

**r2.1 (2.12, medium): an uncovered finding is dropped from the compiled document when any statement covers the same id for another package.**
- Sentence: under fail-closed off, every uncovered finding in the release-time scan gets an `under_investigation` statement carrying the report's timestamp.
- Code: compile-vex.sh:272-273 adds the vulnerability id to `covered` for any `not_affected` or `fixed` source statement, whatever its subcomponents; compile-vex.sh:364 skips every reported finding whose id is in `covered`. Trivy suppresses only the statement's subcomponent, so the other package's finding stays in the report (uncovered) and gets no statement. Probe in /tmp/r2probe (copy of compile-vex.sh and definition-lib.sh): CVE-2026-1 scoped to package a, reported in package b, produced no under_investigation statement; CVE-2026-2 did.
- Same function in the rescan: reattest.sh:201-207 compiles through the same script, so the daily document never gains it either.
- Who: the published status (SECURITY.md promise 2) and every consumer reading the OpenVEX document; the cve issue is still filed from the report (rescan-report reads the reports), so the owner sees it there. A consumer's Trivy still reports it (subcomponent mismatch), so no scanner is misled; the document is silent.
- Reached only when the finding appears after the pull request's gate (the gate counts it uncovered and fails, build.yml:896-916), which is exactly the case Req 2.12 exists for.

**r2.2 (2.21, 2.22, 2.24, medium): the daily checks cover the repositories named by definitions on disk, not the registry namespace.**
- Sentence: 2.21 "every catalogue repository under its declared registry namespace"; 2.22 "every catalogue tag in every catalogue repository"; 2.24 "every digest a catalogue tag references".
- Code: enumerate-catalogue.sh:57-67 builds the repository list from `image/*/image.yaml`; check-visibility.sh:100-103 likewise; verify-catalogue.sh:76-78 reads the enumeration. Nothing lists the namespace in the registry.
- Evidence it is reached: triage/LOG.md:4260 (2026-11-08): after drill-app's level-2 retirement (directory removed), "no drill-app tag enumerated". Whether drill-app's tags still resolve in ghcr.io is registry state the files cannot show; LOG 2026-11-07 records the scheduled rebuild republishing it (sha256:daeef9400b83) before retirement.
- Who: a consumer pulling a tag in such a repository gets a digest no longer scanned, re-attested, visibility-checked or admission-proved, with a green rescan. Also README.md:72-74 ("Every digest a catalogue tag references ... the daily admission proof holds it to that") claims more than the code checks.

**r2.3 (2.22, medium): a failed manifest scan in the rescan leaves the run green.**
- Code: rescan.yml:145-149 (no `set -e`), :200-206 (`::warning::`, `failed++`), :210-217 (step ends 0); reattest.sh:134-140 records `skipped` and :276 fails only on `failed`; rescan.yml:954 shows the count in the summary only. The lifecycle keeps issues open for an unscanned supported digest (lifecycle.go:257-273, :367-368), but nothing fails the run.
- Who: the owner's view, a green rescan on a day a manifest was not scanned; that manifest's attestations are not refreshed.
- Documents that say otherwise: design.md:1697 (error table: "Trivy DB outage ... daily rescan soft-fails with issue"; no issue is filed and the run does not fail); design.md:1229-1230 ("the run fails once, naming every promise not kept that day"); user-manual.md:620 ("every platform manifest scanned by digest"). docs/lanes.md:731 and :757 draw the code correctly.

**r2.4 (2.5, medium): one definition's failed build does not stop the other legs of the run from publishing.**
- Code: build.yml:182-185 `fail-fast: false` over the definitions matrix; each leg's release steps depend on its own steps only.
- Sentence: "publish no artifacts from that run".
- Who: a merge touching two definitions, or the nightly over seven: the healthy ones release while the run is red. Arguably the intended design (docs/lanes.md:557 says so), but the sentence is per run.
- Documents: build.yml:13-14 ("Any failure publishes nothing (Req 2.5)") and user-manual.md:506 ("A failed step publishes nothing and reports itself (Req 2.5)") state the per-run reading. Within one leg the code holds: a later failure leaves the digest pushed and possibly signed but untagged, so frozen (user-manual.md:657-658 says this correctly).

**r2.5 (2.3, low): only the version segment of a tag is checked.** lint-pins.sh:242-252 checks that each tag begins with the declared major, minor or full version. The base-OS segment is a literal in refresh-definition.sh:119-120, compared with nothing (not with the definition's `version-id`); the variant segment is compared with nothing; tag count and order are unchecked, while build.yml:380-382 takes the last tag as the full release tag. Who: a base bump or a reordered list would publish tags whose OS segment lies, or point the comparator at an alias tag.

**r2.6 (2.16, low): the difference is not reported for two of the publishing reasons.** package-set-diff.sh:152-155 (`platform-set-differs`) and :174-177 (`attestation-unreadable`) emit a reason and stop, with no package-set difference, though a published digest carries the tag. The digest that is then pushed comes from a second build (build.yml:414-451, "a replay of the local one" on the gha cache, build.yml:419), not from the compared archive.
