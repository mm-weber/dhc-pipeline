### Description

The catalogue aims at SLSA Build Level 2. Measured against SLSA v1.2 (released 2025-11-24; read from slsa-framework/slsa, branch `releases/v1.2`, commit ae7fc76), it meets Build L1 and the hosted half of L2 and misses the other half: provenance that consumers can authenticate and whose data comes from the build platform rather than from the job. BuildKit attaches provenance to every release (`provenance: mode=max`), but as unsigned attestation manifests written by the job itself; the verification policy never asks for them, and the consumer instructions say so (Req 2.25).

This track adds what L2 needs: one provenance attestation per index and per platform manifest at release, generated by GitHub's provenance service (`actions/attest-build-provenance`) from the signed OIDC token's claims and signed keyless under the build workflow's identity; the expectations a verifier checks, declared in the policy file; a policy rule, a consumer step and a smoke-test assertion; a daily coverage report; and a security-policy statement that never claims above what the policy demands. The requirement binds from the successor's first release (task 12.1): publish-on-change never re-releases an unchanged digest and provenance cannot be minted after the fact, so in this repository it is attested and reported, not demanded.

### Why it was never built (read 2026-10-28)

No decision was taken against it. The cluster A review of 2026-08-21 offered "require provenance in 2.10 and 2.23, or state in 2.25 that it is attached and not verified"; the revision of 2026-08-22 (ledger row 1.14, #97) took the second for 2.25 and added provenance to 2.10, but not to 2.23, with no reason recorded. The review of 2026-09-09 found the provenance leg never asserted (finding 2.4) and none of its eight proposed dispositions carried it. The only SLSA scope ever written is the non-goal "full SLSA L3 hermeticity"; `docs/concepts.md` calls the catalogue "L2-ish". Decision 15 records this.

### The SLSA v1.2 gap, clause by clause

| v1.2 clause | Level | State | Delta |
| --- | --- | --- | --- |
| Provenance exists, identifies the output by digest | L1 | met (BuildKit, per platform manifest) | none |
| Producer distributes provenance | L1 | met (inside the index) | none |
| Hosted build platform | L2 | met (GitHub-hosted runners; only the build workflow's identity on main is admitted) | none |
| Provenance is authentic: signature consumers can validate | L2 | not met (no envelope signature; the index signature covers it only transitively, which no verifier reads) | 2.27 |
| Provenance is authentic: data from the control plane, not the tenant | L2 | not met (BuildKit writes builder and invocation from the job's own values) | 2.27 |
| Consumer validates authenticity and expectations (verifying-artifacts steps 1 and 2) | L2 | not met (no policy rule, no instruction) | 2.25, 2.28 |
| Provenance is unforgeable, isolated builds | L3 | out of scope | Decision 15 option D, not built |

## Functional requirements (EARS)

The subject names follow design.md: the CI Pipeline (`build.yml`), the Scan Pipeline (`rescan.yml`), the Catalogue, the Repository, the verification policy.

### FR-1: Provenance at release (Req 2.9, 2.27)

WHEN criterion 2.9 attests a pushed digest THE CI Pipeline SHALL attest to that digest and to each platform manifest, before the tags, a SLSA provenance attestation (predicate type `https://slsa.dev/provenance/v1`) generated from the build platform's signed workload identity token, signed keyless under the build workflow's identity at refs/heads/main and stored in the declared registry namespace beside that digest; IF that attestation fails THEN THE CI Pipeline SHALL apply no tag and SHALL name the digest.

**Acceptance criteria:**

- [ ] A release run whose digest and every platform manifest carry the attestation, verified with ADR 0005's verifier against the declared identity and expectations
- [ ] The builder identity, build type, repository, workflow path, ref and commit in the predicate equal the token's claims (read from the run)
- [ ] `lint-workflow-policy.sh .` green with `attestations: write` declared; the rescan workflow attests no provenance

### FR-2: The declaration and the policy rule (Req 2.23, 2.28, 7.7)

THE Repository SHALL declare the provenance expectations and the predicate type in `catalogue-policy.yaml`, and WHERE that file's required attestations name SLSA provenance THE verification policy SHALL admit an image only with that attestation from the build workflow's identity whose fields equal the expectations.

**Acceptance criteria:**

- [ ] `render-verification.sh --check` green in both shapes (provenance not required: no rule; required: the rule), each shape covered by a suite case
- [ ] An offline `kyverno apply` of the required shape rejecting a pre-track supported digest by name and admitting a post-track digest

### FR-3: Coverage reported daily (Req 2.29)

WHILE the policy file's required attestations do not name SLSA provenance THE Scan Pipeline SHALL report once per day, for every supported digest, whether it carries an admissible provenance attestation, and SHALL not fail the run on an absent one.

**Acceptance criteria:**

- [ ] `check-provenance.sh` suite green (report and require modes)
- [ ] A scheduled rescan whose status data and issue carry the coverage line, the uncovered digests named

### FR-4: Consumer instructions and the smoke test (Req 2.25, 9.13)

THE Repository SHALL give in its verification instructions one step verifying a digest's SLSA provenance against the issuer, the identity and the expectations, SHALL state which digests carry it, and SHALL describe BuildKit provenance as supplementary detail no policy verifies; the consumer smoke test SHALL run that step verbatim and SHALL fail on a null or unverified result.

**Acceptance criteria:**

- [ ] README and manual blocks rendered, drift check green
- [ ] `consumer-smoke_test.sh` holds a case where an empty provenance result fails (finding 2.4 of the 2026-09-09 review)

### FR-5: The claim, stated (Req 9.19)

THE Repository SHALL state in `SECURITY.md` the SLSA Build level it claims, measured against SLSA v1.2, the digests the claim covers and how a consumer verifies it, and SHALL claim no level above the one its verification policy demands: Build L1 here with L2-grade provenance from the release-path merge, Build L2 from the successor's epoch.

**Acceptance criteria:**

- [ ] The SLSA section in `SECURITY.md`; `docs/concepts.md`'s "L2-ish" sentence replaced; the trust-boundary table names the provenance service

### FR-6: The evidence (Req 7.11)

THE Repository SHALL flip ledger rows 2.27 and 2.29 to `exercised`, measure 9.19 present, leave 2.28 to the successor's first proof, and add the LOG entry, in an evidence pull request.

**Acceptance criteria:**

- [ ] `scripts/lint-live-evidence.sh .` green; `scripts/lint-log-anchors.sh all .` green; task group 18 ticked; this track listed under Completed

## Scope

### In scope

- The spec amendment and this track (phase 0, this pull request)
- The verifier measurement and ADR 0005 (a scratch image outside the catalogue namespace)
- The release step, the coverage report, the declaration and its renderings, the smoke-test assertion, the security statement, the evidence

### Out of scope

- Build L3 (an isolated reusable workflow or slsa-github-generator): named in Decision 15 as option D, not built
- Requiring provenance in this repository's verification policy: the successor's first release does that (task 12.1)
- Re-releasing published digests to back-fill provenance, or any provenance from the rescan's identity
- Replacing the build backend, reproducible builds, the SLSA Source track (the always-on administrator bypass would limit it; a separate question)
- Signing or verifying BuildKit's provenance (Decision 15 option A, rejected)
