### Description

The catalogue aims at SLSA Build Level 2. Measured against SLSA v1.2 (released 2025-11-24; read from slsa-framework/slsa, branch `releases/v1.2`, commit ae7fc76), it meets Build L1 and the hosted half of L2 and misses the other half: provenance that consumers can authenticate and whose data comes from the build platform rather than from the job. BuildKit attaches provenance to every release (`provenance: mode=max`), but as unsigned attestation manifests written by the job itself; the verification policy never asks for them, and the consumer instructions say so (Req 2.25).

This track adds what L2 needs: one provenance attestation per index and per platform manifest at release, generated by GitHub's provenance service (`actions/attest-build-provenance`) from the signed OIDC token's claims and signed keyless under the build workflow's identity; the expectations a verifier checks, declared in the policy file; a policy rule, a consumer step and a smoke-test assertion; a daily coverage report; and a security-policy statement that never claims above what the policy demands. The requirement binds from the successor's first release (task 12.1): publish-on-change never re-releases an unchanged digest and provenance cannot be minted after the fact, so in this repository it is attested and reported, not demanded.

### Why it was never built (read 2026-10-28)

No decision was taken against it. The cluster A review of 2026-08-21 offered "require provenance in 2.10 and 2.23, or state in 2.25 that it is attached and not verified"; the revision of 2026-08-22 (ledger row 1.14, #97) took the second for 2.25 and added provenance to 2.10, but not to 2.23, with no reason recorded. The review of 2026-09-09 found the provenance leg never asserted (finding 2.4) and none of its eight proposed dispositions carried it. The only SLSA scope ever written is the non-goal "full SLSA L3 hermeticity"; `docs/concepts.md` calls the catalogue "L2-ish". Decision 15 records this.

### The SLSA v1.2 gap, clause by clause

| v1.2 clause | Level | State | Delta |
| --- | --- | --- | --- |
| Provenance exists, identifies the output by digest | L1 | met (BuildKit, per platform manifest) | none |
| Producer distributes provenance | L1 | met (inside the index) | none |
| Hosted build platform | L2 | met (GitHub-hosted runners; only the build workflow's identity on main is admitted) | none |
| Provenance is authentic: signature consumers can validate | L2 | not met (no envelope signature; the index signature covers it only transitively, which no verifier reads) | 2.27 |
| Provenance is authentic: data from the control plane, not the tenant | L2 | not met (BuildKit writes builder and invocation from the job's own values) | 2.27 |
| Consumer validates authenticity and expectations (verifying-artifacts steps 1 and 2) | L2 | not met (no policy rule, no instruction) | 2.25, 2.28 |
| Provenance is unforgeable, isolated builds | L3 | out of scope | Decision 15 option D, not built |

## Functional requirements (EARS)

The subject names follow design.md: the CI Pipeline (`build.yml`), the Scan Pipeline (`rescan.yml`), the Catalogue, the Repository, the verification policy.

### FR-1: Provenance at release (Req 2.9, 2.27)

WHEN criterion 2.9 attests a pushed digest and the policy file's provenance mode is not off THE CI Pipeline SHALL attest to that digest and to each platform manifest, before the tags, a SLSA provenance attestation (predicate type `https://slsa.dev/provenance/v1`) generated from the build platform's signed workload identity token, signed keyless under the build workflow's identity at refs/heads/main and stored in the declared registry namespace beside that digest, in the attestation layout the other attestations use, with no Sigstore bundle beside that digest (amended 2026-11-13); IF that attestation or its storing fails THEN THE CI Pipeline SHALL apply no tag and SHALL name the digest.

IF the release's self-check of a pushed digest cannot be made, because its call, the policy file, a value it reads from the policy file or from the environment, or a tool it needs cannot serve, THEN THE CI Pipeline SHALL apply no tag, SHALL ask no verifier about that digest, and SHALL name what could not serve (the argument, the file, the key, the variable or the tool), each cause told apart from every other cause and from a provenance statement that fails the check (added 2026-11-17, the owner's call after the report on plan step 2.5).

WHEN the bundles file holds more than one statement that names a digest THE CI Pipeline SHALL store, of the statements of predicate type `https://slsa.dev/provenance/v1` among them, the one whose log entry is the latest, and a statement of another predicate type SHALL decide nothing about which one is stored; IF no statement of that predicate type names the digest THEN THE CI Pipeline SHALL store nothing, SHALL apply no tag and SHALL name the digest (added 2026-11-18, the owner's call after the code review of pull request 414, finding 1).

IF the bundles file cannot be read as JSON, or holds an entry that is not a Sigstore bundle with a signed envelope whose statement can be read, THEN THE CI Pipeline SHALL store nothing beside any digest, SHALL apply no tag and SHALL name the first digest and that the bundles file cannot be read, in one error line of its own and not in the words of the tool that failed on it; IF the bundle chosen for a digest lacks its signing certificate, or its log entry lacks its integrated time, its log index or its log's id, or holds one of the first two as something other than a whole number, THEN THE CI Pipeline SHALL store nothing beside any digest, SHALL apply no tag and SHALL name that digest and the part that is missing, in the same way (added 2026-11-18, finding 2; a bundle with no log entry at all keeps the refusal it had).

IF the registry answers that no attestation manifest exists beside a digest THEN THE CI Pipeline SHALL store nothing, SHALL apply no tag and SHALL name the digest and that its other attestations must exist first, at that first answer and without a further attempt; IF the pull of that manifest fails three times for any other cause THEN THE CI Pipeline SHALL store nothing, SHALL apply no tag, SHALL name the digest and that the pull failed, and SHALL not state that the manifest is absent (added 2026-11-18, finding 7).

IF the attestation manifest beside a digest is no longer the one the store read when the store is about to write it THEN THE CI Pipeline SHALL not write the layout it prepared from the earlier read and SHALL prepare that digest again from the manifest now there; IF that manifest has changed at three such attempts in a row THEN THE CI Pipeline SHALL apply no tag and SHALL name the digest (added 2026-11-18, finding 8; the registry offers no conditional write, so a writer between this comparison and the write itself is not seen).

WHEN the release's self-check runs THE CI Pipeline SHALL check the index and every platform manifest before the step ends, SHALL name each digest that fails the check or cannot be checked, and SHALL apply no tag if there is one (added 2026-11-18, finding 9).

- [ ] On that released digest cosign 2.6.5 still verifies the signature and every other attestation, and no `sha256-<hex>` tag without a suffix exists (added 2026-11-13)
- [ ] `unpack-provenance_test.sh` and `check-provenance_test.sh` green: the layer's five parts, the other layers untouched, a second unpack replacing its own layer, each refusal by name with nothing written (added 2026-11-13)

### FR-2: The declaration and the policy rule (Req 2.23, 2.28, 7.7)

THE Repository SHALL declare the provenance expectations and the predicate type in `catalogue-policy.yaml`, and WHERE that file's provenance mode is required THE verification policy SHALL admit an image only with that attestation from the build workflow's identity whose fields equal the expectations.

The clauses below sharpen that sentence before its first test (added 2026-11-20, the owner's go for phase 4).

THE Repository SHALL declare under `verification.provenance` the predicate type and five expectations, each a string that is not empty: the builder identity, the build type, the source repository, the workflow path and the ref.

WHEN the self-check or the coverage check judges a provenance statement THE CI Pipeline and THE Scan Pipeline SHALL compare the statement's five fields with the five declared values, for equality, and SHALL derive none of them from the build workflow's identity.

IF the declaration is absent, or lacks one of the five expectations or the predicate type, or holds one of them as anything but a string that is not empty, or declares a predicate type other than `https://slsa.dev/provenance/v1`, THEN the check SHALL not be made, no verifier SHALL be asked, and the key that cannot serve SHALL be named by its dotted path, as FR-1 has it for every other value of the policy file.

WHERE the policy file's provenance mode is required THE Repository SHALL render into the verification policy one more attestation of the existing image entry: the declared predicate type, the releaser's identity under the declared issuer, and the five declared values as conditions of equality on the statement's fields; WHERE the mode is report or off THE Repository SHALL render no such attestation, and the rendered policy SHALL equal the one rendered before this track.

IF the committed policy or a committed instruction block differs from what the policy file renders, in any of the three modes, THEN the drift check SHALL fail naming the file (Req 7.9).

**Acceptance criteria:**

- [ ] `render-verification.sh --check` green in every shape (mode `off` or `report`: no rule; `required`: the rule), each shape covered by a suite case
- [ ] An offline `kyverno apply` of the required shape rejecting a pre-track supported digest by name and admitting a post-track digest

### FR-3: Coverage reported daily (Req 2.29)

WHILE the policy file's provenance mode is report THE Scan Pipeline SHALL report once per day, for every supported digest, whether it carries an admissible provenance attestation, and SHALL not fail the run on an absent one.

The five clauses below sharpen that sentence before its first test (added 2026-11-19, the owner's go for phase 3; what "every supported digest" takes in and what ends the check are the session's reading, put to the owner with the step's report).

WHEN the coverage check is asked about one or more references THE Scan Pipeline SHALL ask each of them, in the order given, the question the release's self-check asks of one digest (FR-1: signed under the declared issuer and the build workflow's identity, and the five expectations met), and SHALL print for each reference one line that names it and says whether it is covered, and for one that is not covered what the self-check would have said of it.

IF a reference carries no admissible provenance attestation, or the question about it stays unanswered after the self-check's attempts, THEN THE Scan Pipeline SHALL report that reference as not covered, SHALL write no error line for it, SHALL go on to the next reference and SHALL not fail the run for it.

IF the coverage check cannot be made, because its call, a reference it is given, the policy file, a value it reads from the policy file or from the environment, or a tool it needs cannot serve, THEN THE Scan Pipeline SHALL ask no verifier about any reference, SHALL print no state for any reference and SHALL fail the run naming what could not serve, each cause told as the self-check tells it: a check that was never made is not a day without coverage.

WHERE the policy file's provenance mode is required THE Scan Pipeline SHALL ask every reference the same way, SHALL print the same lines, SHALL write one error line for each reference that is not covered, and SHALL fail the run if there is one, after the last reference was asked (the successor's position; built here, used there).

WHILE the policy file's provenance mode is report or required THE Scan Pipeline SHALL give that check every supported digest and each platform manifest under it, the references a release attests (FR-1), and SHALL state in the status data and in the status issue how many of them are covered, of how many, naming each that is not.

**Acceptance criteria:**

- [ ] `check-provenance.sh` suite green (report and require modes): one line per reference in the order given, an uncovered reference reported with exit 0 and no error line, a check that cannot be made ending with exit 2 before any reference is asked, `require` ending with exit 1 and one error line per uncovered reference after all were asked (sharpened 2026-11-19; plan 3.1, 3.2)
- [ ] A scheduled rescan whose status data and issue carry the coverage line, the uncovered digests named

### FR-4: Consumer instructions and the smoke test (Req 2.25, 9.13)

THE Repository SHALL give in its verification instructions one step verifying a digest's SLSA provenance against the issuer, the identity and the expectations (the five declared values, rendered into the step; sharpened 2026-11-20), SHALL state which digests carry it, and SHALL describe BuildKit provenance as supplementary detail no policy verifies; the consumer smoke test SHALL run that step verbatim and SHALL fail on a null or unverified result. WHERE the provenance mode is off the instructions SHALL state that releases attest none and give no step, and the smoke test SHALL run none.

**Acceptance criteria:**

- [ ] README and manual blocks rendered, drift check green
- [ ] `consumer-smoke_test.sh` holds a case where an empty provenance result fails (finding 2.4 of the 2026-09-09 review)

### FR-5: The claim, stated (Req 9.19)

THE Repository SHALL state in `SECURITY.md` the SLSA Build level it claims, measured against SLSA v1.2, the digests the claim covers and how a consumer verifies it, and SHALL claim no level above the one its verification policy demands: Build L1 here with L2-grade provenance from the release-path merge, Build L2 from the successor's epoch. WHERE the provenance mode is off the statement is Build L1 with no SLSA provenance attested while it stands.

**Acceptance criteria:**

- [ ] The SLSA section in `SECURITY.md`; `docs/concepts.md`'s "L2-ish" sentence replaced; the trust-boundary table names the provenance service

### FR-7: The provenance mode and its off position (Req 2.30, 7.7; added 2026-11-11, the owner's call)

THE Repository SHALL declare in `catalogue-policy.yaml`'s release section one provenance mode, `off`, `report` or `required`, read through `release-policy.sh`; WHERE that mode is off THE CI Pipeline SHALL attest no SLSA provenance and SHALL release otherwise unchanged, and THE Scan Pipeline SHALL state in its daily report that provenance is off and SHALL verify none.

**Acceptance criteria:**

- [ ] `release-policy_test.sh` holds the three accepted values and a refusal by name for a missing key and for a value outside them
- [ ] One release with the mode `off` through a normal pull request and back: every other signature and attestation present, no provenance attestation, the rescan's line stating that provenance is off

## Scope

### In scope

- The spec amendment and this track (phase 0, this pull request)
- The verifier measurement and ADR 0005 (a scratch image outside the catalogue namespace)
- The release step, the coverage report, the declaration and its renderings, the smoke-test assertion, the security statement, the evidence
- The provenance mode with its `off` position (the amendment of 2026-11-11), built with the release step

### Out of scope

- Build L3 (an isolated reusable workflow or slsa-github-generator): named in Decision 15 as option D, not built
- Requiring provenance in this repository's verification policy: the successor's first release does that (task 12.1)
- Re-releasing published digests to back-fill provenance, or any provenance from the rescan's identity
- Replacing the build backend, reproducible builds, the SLSA Source track (the always-on administrator bypass would limit it; a separate question)
- Signing or verifying BuildKit's provenance (Decision 15 option A, rejected)
